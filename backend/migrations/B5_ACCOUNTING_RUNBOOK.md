## 本地验证与生产发布要求

1. 核对 Git 工作区、线上代码哈希、阿里云真实 schema 和只读异常报告；
   若代码或表结构不符，停止对应部署。
2. 制作并校验*新鲜*的完整 MySQL + 源码 + 上传文件备份，限制备份权限，
   不显示内容。准备维护窗口和 B4 代码回退副本。
3. 在隔离测试数据库先运行 `npm run migration:b5 -- --plan`，经审阅后
   `npm run migration:b5 -- --apply --confirm=B5-ADDITIVE-MIGRATION`，
   再次 `--plan` 应显示全部已应用。测试租号创建/取消、重复请求、账务回滚、
   人工付款凭证关联、管理员确认实际收款、租用方确认完单、争议及人工退款、
   三方订单逐笔最终确认。用两个独立测试账户，不碰真实历史订单。
4. 只有获得对**生产库上述三份加法迁移**的单独授权后，才在维护窗口
   按同一顺序执行。不可运行 `DROP`、`TRUNCATE`、`DELETE`，不可批量改历史余额、
   支付状态、收益或三方订单。
5. 表结构/代码必须配套部署，先迁移后代码；重启单实例 PM2，检查静态页、
   健康接口、只读业务接口和聚合记录数。B3 的 6 元真实支付宝回归仍另行验收。

## 回滚与未完成边界

- MySQL DDL 无法整体事务回滚；新表保留，切回 B4 代码可停止 B5 新功能，
  不能 DROP 新表，也不能让 B4 覆盖 B5 已写入的流水/审计。
- `schema_migrations` 记录脚本 SHA-256；迁移文件改动后会拒绝把同一版本
  静默重跑。`CREATE TABLE IF NOT EXISTS` 后会核对关键类型/唯一约束。
- 历史余额的期初流水、历史截图关联、已付款三方订单最终状态、退款和
  外键异常修复均须先出只读报告，再逐项审批。不能自动推断历史账务。
- 新代码已覆盖注册推荐积分、常规订单/租号抵扣、商城积分、打手完单
  收益与积分、签到与开箱券、支付宝 6 元充值券的**新发生变动**；上线
  后仍需两个账户的真实业务流程验收。历史余额尚无期初流水，不能
  将 `SUM(amount_delta)` 当作全部历史余额，也不能声称完整资金总账。
- 已获业主确认的租号规则：管理员逐笔核实实际收款并填写核对编号；出租方
  只能申请完成；租用方确认或管理员处理争议后，才计入出租收益。付款凭证
  截图只是待核实材料，不代表到账。已付款订单不得自行取消并自动退积分；
  管理员先在外部核实全额退款（现金为 0 时核实无现金应退），登记金额和
  凭据编号后，才取消并退还抵扣积分。本站不自动发起退款、不读取支付宝密钥。
- 管理面板的租号人工订单列表最多显示最近 100 条；管理员须人工核实收款、
  退款与争议材料，不能仅凭截图点“通过”。接口只记录人工结论，不验证
  收款渠道是否真的完成交易。生产发布后仍需单独验收该人工流程。
