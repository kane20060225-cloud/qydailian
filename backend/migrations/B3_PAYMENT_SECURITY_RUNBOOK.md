# B3 支付安全发布手册

B3 必须独立评审和发布。首次验证只使用支付宝沙箱与隔离数据库，不得用生产用户进行试付或补单。

## 当前兼容边界

- 迁移只给 `payment_orders` 新增支付宝交易号、支付/关闭时间、更新时间和查询索引，不删除或改写历史订单。
- 历史 `paid` 订单允许交易号为空；收到签名、金额、应用和卖家均匹配的重复通知时，只补交易号，不重复加券。
- 历史 `pending` 订单不会自动关闭。必须先运行聚合报告并完成支付宝侧对账，再决定逐单处理方式。

## 沙箱验证顺序

1. 备份隔离数据库，并确认应用代码与目标环境一致。
2. 执行 `20260914_b3_payment_integrity.sql`，只读核对新增列与索引。
3. 配置 `ALIPAY_ENVIRONMENT=sandbox`、沙箱网关、沙箱应用 ID、卖家 ID 和 HTTPS 回调地址。
4. 运行 `npm test`，再运行 `npm run payment:b3:report`。
5. 在沙箱创建一笔充值，验证支付成功只加一次券。
6. 重放同一回调，确认不重复加券；再测试错误金额、错误应用、错误卖家和乱序状态。
7. 检查日志仅包含脱敏商户订单引用和处理结果，不包含完整通知体、用户 ID 或支付表单。

## 生产发布前置条件

1. 新建生产数据库与应用备份并验证可恢复。
2. 只读导出 113 条历史 `pending` 的对账清单供人工核对；不得批量直接关闭。
3. 在生产 `.env` 中补充 `ALIPAY_ENVIRONMENT=production` 与 `ALIPAY_SELLER_ID`，并确认网关为生产网关。不得输出变量值。
4. 安排短维护窗口：先迁移表结构，再部署应用，在临时端口完成配置预启动后切换 PM2。
5. 只做零金额风险的状态查询和历史重复通知验证；真实小额支付必须再次取得明确授权。

## 回滚

- 应用可以回滚到 B2，但回滚后应暂停支付宝回调入口，避免旧逻辑再次处理重复通知。
- 新增列和索引保留，不执行 `DROP COLUMN` 或缩表操作。
- 若 B3 已成功入账，禁止通过直接扣券回滚；必须按支付对账和账务流程处理。
