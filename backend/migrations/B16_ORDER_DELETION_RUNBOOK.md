# B16 订单删除申请与历史异常核对

本批同时发布 B15 三步下单、订单指引、租号筛选和管理员待办指标。

## 使用

- 打手在三方订单卡片点击“申请删除”，进入详情填写重复提交等原因。只能申请自己的订单；申请不会直接隐藏订单或改变付款和执行状态。
- 管理员从订单中心“删除申请”待办打开详情，选择同意或驳回。驳回必须填写原因；同意必须填写核对依据并确认记录保留。
- 已审核或执行中的重复三方订单，以及执行/收款状态不一致的历史代练订单，管理员详情提供“核对后删除（保留记录）”。核对另一笔有效订单、测试依据、实际收款与交付情况，确认无需继续履约后操作。
- 客户自己的历史异常代练订单也可申请核对删除。异常订单不再直接提供上传付款凭证入口，以免诱导再次付款。
- 删除仅移入回收站，原始订单状态、付款、余额、游戏资料、接单、交付、资金流水和操作记录保留。核对删除的记录长期保留，不参加14天自动永久清理。普通安全无资金订单继续沿用原删除规则。
- 管理员可从回收站恢复。真实业务或付款状态发生变化时，原删除快照失效，订单重新可见，避免隐藏后续资金或执行变化。
- 本批不自动删除图片中的真实订单，也不批量取消、退款或改写历史收款状态；上线后可逐笔核对操作。

## 发布

新增表仅为 `order_deletion_requests`，不修改现有订单、流水或余额表。

1. 备份生产站点、数据库和本批运行文件。
2. 在生产表结构副本、专用空测试库运行 `verify-order-deletion-isolated.js --database=qydailian_b16_test_<suffix>`；仅允许合成数据和专用测试账号。
3. 在现有 B14 环境执行 `node scripts/migrate-b16-order-deletion.js --plan`，再执行 `--apply --confirm=B16-ORDER-DELETION-ADDITIVE-MIGRATION`。
4. 确认新增表结构及版本记录，部署本批前后端白名单文件，保留 `.env`、上传文件和依赖。
5. 重启 `my-backend`，检查健康接口、公网文件哈希、匿名权限及管理员只读详情。

回滚使用发布目录的运行文件备份。新增审核表保留，不删除任何审核记录。B14 的超时关闭开关保持原值。

## 验证

本地220项后端测试通过。桌面1440×1000与手机390×844验证打手申请、管理员核对确认、回收站记录保留、恢复和历史接单代练异常删除；B15下单、原订单中心、B14生命周期、通知与打手状态浏览器回归通过。服务器专用MySQL副本及正式部署结果记录于发布报告。
